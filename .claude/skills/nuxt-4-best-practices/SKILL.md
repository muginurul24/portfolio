# Nuxt 4 Best Practices

Apply these patterns when authoring or reviewing Nuxt 4 code. Goal: correct SSR
hydration, single-fetch data, lean plugins, and strong Core Web Vitals.

Sources: [hydration](https://nuxt.com/docs/4.x/guide/best-practices/hydration),
[performance](https://nuxt.com/docs/4.x/guide/best-practices/performance),
[plugins](https://nuxt.com/docs/4.x/guide/best-practices/plugins),
[data fetching](https://nuxt.com/docs/4.x/getting-started/data-fetching),
[llms-full](https://nuxt.com/llms-full.txt).

For deeper recipes see:
- `references/hydration.md` — mismatch causes and fixes
- `references/performance.md` — links, hybrid render, lazy, assets, profiling
- `references/plugins.md` — when to plugin, parallel async, object syntax
- `references/data-fetching.md` — useFetch / useAsyncData / $fetch rules

## Decision checklist (run first)

1. **Initial page/component data?** → `useFetch` or `useAsyncData` with an
   explicit key. Never bare `$fetch` in setup for SSR-shared data.
2. **User event (submit, click, mutation)?** → `$fetch` (or form actions).
3. **One-time side effect (store hydrate, analytics init)?** → `callOnce` or
   `onMounted`, not a data-fetch composable.
4. **Browser-only API / DOM / third-party widget?** → `onMounted`, `.client`
   plugin, or `<ClientOnly>` with a useful fallback.
5. **Heavy or below-fold UI?** → `Lazy*` component; add lazy hydration
   (`hydrate-on-visible`, etc.) when interactivity can wait.
6. **Secret vs public theme token?** → `runtimeConfig` vs `app.config`.
7. **Route needs different cache/SSR mode?** → `routeRules` hybrid rendering.
8. **New global capability?** Prefer a composable first; only add a plugin when
   app-wide registration is required.

## Data fetching (highest leverage)

SSR-safe initial data ships through the Nuxt payload so the client does not
refetch and does not diverge from the HTML.

```vue
<script setup lang="ts">
// ✅ Initial data — deduped server→client
const { data: templates } = await useFetch('/api/templates', {
  key: 'templates',
})

// ✅ Explicit key when wrapping custom logic
const route = useRoute()
const { data: product } = await useAsyncData(
  `product:${route.params.slug}`,
  () => $fetch(`/api/products/${route.params.slug}`),
)

// ✅ Client interaction only
async function placeOrder(body: OrderBody) {
  return await $fetch('/api/orders', { method: 'POST', body })
}
</script>
```

```ts
// ❌ Double fetch + hydration risk
const data = await $fetch('/api/templates')
```

Rules of thumb:
- Always pass your own **key** to `useAsyncData` / `useFetch` when reusable or
  param-dependent; autogenerated keys use file+line only and break custom
  composables.
- Same key ⇒ same `handler` / `transform` / `pick` / `getCachedData` / `default`
  / `deep`. Differ `server`, `lazy`, `immediate`, `watch`, `dedupe` only.
- Side effects do not belong in the fetch handler — use `callOnce`.
- Shrink payload with `pick` or `transform`.
- Non-blocking client nav: `lazy: true` / `useLazyFetch` and handle `status`.
- Client-only fetch: `{ server: false, lazy: true }` and never assume `data`
  is set during setup before hydration finishes.
- Server `$fetch` that needs cookies: prefer `useFetch` (uses `useRequestFetch`)
  or pass a tight header allowlist via `useRequestHeaders(['cookie'])`.
  Do **not** forward `host`, `accept`, `content-length`, `content-type`,
  `x-forwarded-*`, `cf-*`.

## Hydration safety

Hydration mismatches force full re-render, hurt TTI, break listeners, and can
desync SEO HTML from what users see. Fix warnings; do not silence them.

| Cause | Prefer |
|-------|--------|
| `localStorage` / `window` / `document` in setup | `useCookie`, CSS breakpoints, or `onMounted` + `ClientOnly` |
| `Math.random()` / `Date.now()` in rendered text | `useState` seed, `NuxtTime`, or client-only update after mount |
| Client-only branch in SSR tree | CSS responsive classes or `ClientOnly` fallback |
| Third-party DOM libs | Dynamic import inside `onMounted` |
| Divergent data sources | One SSR-friendly composable (`useFetch` / `useState`) |

```vue
<script setup lang="ts">
// ✅ Shared random across SSR + client
const token = useState('invite-token', () => crypto.randomUUID())

// ✅ Browser lib after hydrate
onMounted(async () => {
  const { default: Chart } = await import('heavy-chart-lib')
  Chart.mount('#chart')
})
</script>

<template>
  <ClientOnly>
    <WeatherBadge />
    <template #fallback>
      <span>Memuat cuaca…</span>
    </template>
  </ClientOnly>
</template>
```

## Performance

Use built-ins before adding libraries.

- **Links**: `<NuxtLink>` for internal routes (smart prefetch). Tune
  `experimental.defaults.nuxtLink.prefetchOn` if visibility prefetch is noisy.
- **Hybrid rendering**: per-route `routeRules` (`prerender`, `swr`, `isr`,
  `ssr: false`) instead of one global mode.
- **Code split UI**: `LazyMyWidget` for conditional / rare UI.
- **Lazy hydration** (Nuxt ≥3.16): e.g. `<LazyMyWidget hydrate-on-visible />`
  so below-fold blocks do not compete for main-thread interactivity.
- **Images**: `<NuxtImg>` / `<NuxtPicture>` — LCP image `loading="eager"` +
  high fetch priority; others `loading="lazy"`.
- **Fonts**: `@nuxt/fonts` (self-host, fallback metrics → less CLS).
- **Third-party scripts**: `@nuxt/scripts` with explicit triggers; queue calls
  via proxy until loaded.
- **Measure**: `nuxi analyze`, Nuxt DevTools timeline/payload, Lighthouse / PSI.

```ts
// nuxt.config.ts — hybrid example
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },
    '/templates/**': { swr: 3600 },
    '/blog/**': { isr: 3600 },
    '/panel/**': { ssr: false },
  },
})
```

## Plugins

Plugins run during app init / hydration. Costly setup blocks TTI.

1. Prefer a **composable** or utility if callers can import it on demand.
2. Keep plugin bodies thin — register, do not compute heavy work eagerly.
3. Async plugin that can race others: set `parallel: true` so it does not
   serialize the whole plugin chain.
4. Browser-only integrations: name file `*.client.ts` (or guard with
   `import.meta.client` only when structure requires).
5. Object-syntax `name` / `enforce` / `hooks` / `env` must be **static** so Nuxt
   can optimize; do not compute `enforce` from runtime flags.

```ts
// app/plugins/analytics.client.ts
export default defineNuxtPlugin({
  name: 'analytics',
  parallel: true,
  async setup() {
    const { proxy, onLoaded } = useScriptGoogleAnalytics({
      id: useRuntimeConfig().public.gaId,
    })
    proxy.gtag('config', useRuntimeConfig().public.gaId)
    onLoaded(() => { /* ready */ })
  },
})
```

## Config placement

| Need | API |
|------|-----|
| Secrets, env-overridable server values | `runtimeConfig` (`NUXT_*`) |
| Public build-time brand/theme defaults | `app.config` / `defineAppConfig` |

Never put secrets under `runtimeConfig.public`.

## Review anti-patterns

Flag and fix when you see:

- `$fetch` / raw `fetch` in `<script setup>` for initial SSR data
- Autogenerated `useAsyncData` keys inside shared composables
- Pinia/store actions invoked *as* the `useAsyncData` handler for side effects
- `localStorage` / `window` reads that paint into SSR HTML
- Eager third-party scripts in `nuxt.config` head without Nuxt Scripts triggers
- New plugin for something a composable could export
- Full static `<img>` for LCP heroes without dimensions / modern formats
- Ignoring console hydration mismatch warnings

When implementing features: write Nuxt-idiomatic code that passes the checklist
above without being asked.
